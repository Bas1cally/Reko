Decisive re-testing of the TSS stream-flood finding (30 Jul 2026), against the
REAL default go-libp2p v0.32 resource manager (*rcmgr.resourceManager).

1) Single attacker peer, 90s, uncapped: 253,271 streams, 0 rejections, victim
   RSS PLATEAUS at ~180 MiB. No crash. (per-peer RM bound)

2) Legit-stream starvation test (starve_test.go): under a 70,484-stream flood
   from one attacker peer, a legitimate peer's TSS stream was DELIVERED 10/10.
   NOT starved. Reason: the RM isolates per-peer; one attacker peer cannot
   exhaust a different peer's allocation.

3) Multi-peer OOM: 8 peers -> ~1.2 GiB; 20 peers -> OOM at a 2 GiB cap (dmesg).
   40 peers -> plateau ~2 GiB, and attacker-side failures ("connection failed",
   "context deadline exceeded") — NOT victim RM rejections. The ~2 GiB ceiling
   = RAM/8 (the RM's autoscaled default) on the 16 GiB test box; also the point
   my 4-core rig can no longer generate more victim-side load.

CONCLUSION (honest):
- Real bug: readFramed's `make([]byte, length)` (up to 1 MiB) is UNCOUNTED by
  the resource manager -> 4 bytes -> ~1 MiB amplification.
- Impact is BOUNDED by the RM to ~RAM/8 of uncounted memory. It OOM-kills a
  universalClient deployment whose process/container memory limit is below
  ~host_RAM/8 (go-libp2p reads host RAM, not the cgroup, so a container capped
  below that is vulnerable). Proven: OOM at a 2 GiB cap.
- It does NOT crash a generously-provisioned node (plateaus ~RAM/8, degraded).
- It does NOT starve a legitimate peer's stream at single-attacker scale.
- "Kill every validator's TSS node for free" (single peer) is NOT supported.
  The defensible claim is a conditional resource-exhaustion OOM of
  memory-capped deployments — Medium/High at most, not a clean Critical.

4) THE DECISIVE NUMBER — victim's default RM system-wide admission caps (read
   directly from rcmgr.DefaultLimits.AutoScale() on the 16 GiB box):
     SYSTEM StreamsInbound = 3033   (total concurrent inbound streams, ALL peers)
     SYSTEM ConnsInbound   = 189    (total concurrent inbound connections)
     SYSTEM Memory         = 2.09 GB (RM-counted)
     PER-PEER StreamsInbound = 507
   => No attacker "army" can exceed 3033 concurrent inbound streams; beyond that
      the RM rejects ("cannot reserve inbound stream"). Max uncounted memory from
      the make([]byte,1MiB) buffers is therefore ~3033 x 1 MiB ~= 3 GiB,
      REGARDLESS of how many attacker peers/processes/machines are used. This is
      why the earlier same-box multi-attacker plateau (~2 GiB) was NOT purely a
      test artifact — there is a real system-wide stream ceiling just above it.
   => The ceiling autoscales with host RAM (16->~3 GiB, 32->~6, 64->~12), staying
      ~1/5 of RAM, i.e. always below total host RAM. A node whose universalClient
      process may use its host-RAM-proportional share SURVIVES any army (plateaus,
      degraded). OOM occurs ONLY when the process/container memory limit is set
      BELOW the host-RAM-derived ceiling (go-libp2p autoscales from HOST RAM, not
      the cgroup) — e.g. a 2 GiB container on a 16 GiB host. Proven at 2 GiB.
   CONFIRMS round-5 conclusion with a hard mechanism: conditional OOM of
   memory-capped deployments, not an unconditional "kill any validator."

5) CPU-EXHAUSTION VECTOR (RAM-independent) — "how long until overload?":
   The RM caps CONCURRENCY (3033 streams, 189 conns) but NOT the RATE of
   stream/connection open attempts; each costs protocol negotiation
   (multistream-select) / crypto handshake CPU, uncapped.
   - Victim pinned to 1 core, 6 attackers: CPU pegs to 97-99% in ~3-6 seconds
     and stays there. No grace period.
   - Victim unpinned (4 cores), 10 attackers sharing the same box: victim uses
     ~150% CPU (1.5 cores) => the handling PARALLELIZES across cores; it is not a
     single-threaded bottleneck. On separate attacker machines (real case) the
     victim would have all cores free and an army could push more cores to 100%.
   Honest gap: not directly proven that this CPU saturation starves legitimate
   DKLS/TSS work (single-peer starve test still delivered legit streams 10/10;
   couldn't generate an isolated all-core army on a shared 4-core box). But this
   is the stronger, RAM-INDEPENDENT angle for #2 if pursued: rate-based CPU
   exhaustion via connection/stream churn that the RM does not rate-limit.

6) CPU-DENIAL HYPOTHESIS ("flood pegs CPU -> validator rejects legit users too"):
   TESTED with a dedicated legit-peer probe (fresh Connect + NewStream + valid
   frame each iteration), victim pinned/CPU-capped so the flood fully saturates it,
   probe on its own core:
     - victim ~92% of 1 core:      legit 10/10 OK, latency 11ms == baseline (no degradation)
     - victim 100% of a 0.5-core cap (fully saturated): legit 12/12 OK, latency
       12ms -> ~44ms avg, spikes to 161ms. DEGRADATION, NOT DENIAL.
   => Legit peers are NOT rejected even at full CPU saturation. Reason: the RM
      RESERVES per-peer allocations, so an attacker cannot monopolize a legit
      peer's slot; the tiny legit work is still scheduled. TSS ceremonies
      (second-scale timeouts) tolerate ~160ms easily.
   => The "classic CPU-exhaustion rejects everyone" conclusion is DISPROVEN here.
   Untested theoretical residual: exhausting ConnsInbound (=189) with ~189
   persistent attacker connections to block NEW legit connections; the connmgr's
   trimming/peer-protection likely mitigates, but not verified.
   Overall #2 verdict UNCHANGED: bounded/conditional resource exhaustion
   (memory OOM only if capped < host_RAM/8; CPU degradation not denial) = Med/High.
